# fr-review-the-token-efficient-path-for-long-context-inference-kv-cache-offload-t-bd60c176

Let us calculate the KV cache size for MiniMax-M2.7 in FP8, as tested here. With one byte per KV element, the entry per token is 2 × 62 × 8 × 128 bytes, or approximately 124 KiB. This calculation generalizes to any grouped-query attention transformer: the KV cache size per token equals the number of layers × the number of KV heads × the head dimension × 2 (for K and V) × the number of bytes of the data type. Thus, a model with more layers or KV heads writes proportionally more information per token. Under moderate operating conditions (approximately 4,200 tokens per second on the RAM tier), one hour of retention generates approximately 15 million cached tokens, which, at 124 KiB per token, represents approximately 1.8 TB. This represents a significant amount of DRAM and increases the compilation cost.
From this perspective, SLO requirements and budget determine the choice of cache tier. If the SLO is flexible enough that the reload latency of the SSD tier remains acceptable, the second KV cache tier can rely solely on storage, with only the thin RAM buffer required by upstream connectors. The cost of storage is modest: during our tests, peak KV traffic reached 4.1 GB/s write and 1.1 GB/s read, for a maximum throughput measured by fio of approximately 114 GB/s. The RAID 10 array used had 28 times that bandwidth, ensuring that flash storage is not a bottleneck, even when the XE7740 fully utilizes its eight GPUs and supports a larger simultaneous load. This headroom allows the operator to prioritize capacity over speed. Each additional terabyte of D7-PS1030 extends the time-to-live (TTL) and the working set that the system retains in residence, and a larger resident cache means more avoided recomputations and more tokens served.
Endurance is the constraint that defines this tier. A KV offload cache is very write-intensive: each token produced by the model creates a KV entry, and TTL updates cause continuous cache rewriting, so the drives are constantly stressed by writes. On our eight-drive array, the sustained write throughput reached 1.9 GB/s. With the RAID 10 configuration we tested, mirroring doubles the capacity absorbed by the media, which corresponds to approximately 3.2 writes per day on each 12.8 TB drive, slightly above the 3 drive writes per day (DWPD) sustained rating of the D7-PS1030. For primary storage, this rate would be prohibitive, but it is acceptable in this specific case. The cache is designed to be ephemeral, and the failure mode of a worn drive is recomputation, not data loss. RAID 0 is arguably more suitable for this tier for some users, as it distributes data across the eight drives to avoid duplicate writes and reduces the media write rate to approximately 1.6 DWPD, which remains well within allowable limits. In both cases, the conclusion remains the same: this workload consumes endurance faster than any other element of the system, high-endurance dedicated drives have only a fraction of the capacity needed for this level of performance, and it is this combination that makes a high-capacity, write-focused drive like the PS1030 the ideal choice.
Tokens per dollar
The performance section demonstrated that flash memory retains most of the throughput and maintains time to first token, unlike DRAM, when the working set exceeds memory capacity. From a business perspective, the cost of the storage tier is a determining factor. The simplest solution for recomputation is to increase the cost of that expensive DRAM; the case for offloading is only valid if the storage tier is significantly cheaper per unit of capacity.
The most obvious gap lies in capacity, not price. The 512 GB DRAM offload tier is the one that saturated and began flushing the cache; the flash tier, measured in terabytes, is the one that did not. No realistic DRAM budget allows for tens of terabytes of KV cache to be placed near the GPUs. Therefore, beyond a certain context length, the choice is no longer between fast DRAM and flash memory; it is rather a choice between flash memory and context deletion, with deletion being the main cause of throughput loss and latency.
In terms of price, enterprise flash memory has long sold at a fraction of the cost per terabyte of DRAM, a structural gap that stems from the multi-level, 3D-stacked cell design of NAND, as opposed to the one-transistor-one-capacitor design of DRAM. The memory shortage expected for 2026 has driven both prices up significantly, and NAND contract prices have risen at least as fast as DRAM prices throughout the year. So this is not a case of flash memory prices falling due to the DRAM price surge. Even at current levels, the price gap per terabyte persists, and flash memory remains the only solution offering terabyte-scale cache capacity at a cost compatible with a deployment budget.
Throughput and cost converge. At the moment flash memory took the lead, it was processing more tokens per second than DRAM, not fewer. It therefore does not sacrifice throughput for capacity, but offers increased capacity on a less expensive medium per terabyte. In terms of tokens per second per dollar, the advantage is considerable for flash memory, and it grows with data retention duration, because that is precisely where DRAM reaches its limits, unlike flash memory.
DRAM remains the most appropriate memory as long as the working set supports it, and the thin RAM transit buffer required by connectors is always upstream of flash memory. However, adding additional GPUs or DRAM represents the highest cost per terabyte to obtain maximum performance only needed for the workload, until the cache saturates. Offloading or tiering to flash memory preserves most of that performance while maintaining context indefinitely, at an affordable cost per terabyte. The final decision will, however, depend on the service level objective (SLO) requirements of the workload the operator is optimizing.
Conclusion
For inference workloads, tokenomics is at the heart of the debate. The token is the product, and recomputation is waste: the GPU has already generated that context and is forced to rebuild it. Agentic serving is where the stakes are highest, because our week of instrumented Claude Code traffic showed that 98.16% of tokens were cache reads, a context that the GPU had already computed and would otherwise have rebuilt at each eviction. KV cache offloading transforms the prefill computation, which would have served to rebuild that history, into new tokens. On the XE7740, this translated into a total service throughput up to 2.9x higher than the VRAM-only baseline under heavy load, with the model, GPUs, and engine held constant. Where DRAM was saturated and its performance was dragged down, flash memory sustained that throughput with a capacity DRAM cannot match.
This does not, however, call into question the need for DRAM. For short and irregular workloads, where a session opens, runs briefly, and closes before its cache saturates memory, DRAM is the optimal solution, and KV cache offloading provides little benefit. The working set fits, latency is minimal, and there is nothing to evict.
We consider this profile to be the exception, however, where a DRAM tier suffices. Most production inference now runs continuously and over long periods: multi-turn agents, large contexts, steady concurrency, users rejoining the same session. In this case, the working set exceeds the capacity of the memory tier an operator can allocate, the cache is flushed, and the GPU is called back into service to rebuild the context it has already produced. This is the most costly failure mode, and it is common.
