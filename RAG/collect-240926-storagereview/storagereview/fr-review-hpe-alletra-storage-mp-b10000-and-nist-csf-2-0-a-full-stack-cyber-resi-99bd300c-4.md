Both solutions are complementary rather than redundant. Remote Copy preserves the immutability guarantees enforced by the storage array across sites, while Zerto provides checkpoint granularity and orchestrated failover at the virtual machine level. As part of this project, the topology was configured to support Zerto replication from Fort Collins to the HPE Bristol, UK site. However, during the test session, replication ran locally in Fort Collins due to bandwidth and parallel cluster constraints. The Bristol site is deployed as an available topology and for follow-up activity, not as an inter-site disaster recovery demonstration.
Configuration drift detection
The security hardening guide defines a baseline configuration. The continuous audit log stream allows a SIEM to verify, in near real time, that this configuration has not drifted. Changes to password policies, account lockout, creation of new accounts, role elevations, schedule modifications, and replication target changes all appear as queryable events. Since the lab environment did not have a SIEM, drift detection was performed at the B10000 audit log level rather than using a centralized correlation tool. At a customer with a SIEM, these same audit events are forwarded to the SIEM via the syslog integration described in the "Detect" section.
Detect: Visibility and early warning
The B10000 includes a ransomware detection engine that monitors storage I/O operations in real time and generates an alert as soon as a statistical signature of large-scale encryption is detected during writes to the array. The HPE Cybersecurity Center of Excellence has validated this engine against more than 100 of the most significant ransomware strains.
Detection is enabled per data store on the VME side. When a data store is created or modified in VME on a B10000 storage server, the ransomware detection option is enabled by default for each volume provisioned in that data store. Per-volume customization is possible after creation. This feature requires B10000 operating system version 10.5.0 or later. In the Fort Collins lab, the ftc-vme-mg1 data store was configured to connect to the FTC-AMP-5 B10000 server via Fibre Channel, with ransomware detection enabled. This configuration is the one used for the ransomware attack simulation described later in this section.
The B10000 also supports system-wide ransomware detection policies directly on the storage array, allowing administrators to define global detection sensitivity and automatic snapshot retention behavior on protected volumes. As shown below, the Fort Collins environment had the array-level ransomware detection policy enabled with a low-confidence sensitivity profile and automatic snapshot retention configured. This provides an additional layer of protection beyond per-datastore enablement in VME, ensuring that the detection engine remains consistently applied at the platform level, regardless of how individual volumes are provisioned.
The detection logic, for both types of data, relies on entropy. Random data, which corresponds to the appearance of encrypted data at the block level, exhibits high entropy. Legitimate workload data, even compressed, has a structure that the engine recognizes. The engine uses a CuSum entropy calculation to measure the disorder of incoming writes relative to an established baseline value. This baseline value is learned during a training phase, when a new volume is first protected, and then maintained by a rolling one-hour I/O profile, to prevent legitimate workload variations from generating false positives. When entropy deviates from the baseline in a statistically significant way, the engine flags the volume.
For the SOC, the main idea is that this encryption detection engine constitutes a last line of defense for the environment, not a substitute for endpoint protection. It is at the endpoint level that ransomware must be detected first. The B10000 detects what the endpoint let through.
SIEM integration
The integration is deliberately vendor-independent. HPE's role is to provide the infrastructure and tools necessary for the B10000 to integrate audit and security log data into any SIEM already in place within an organization, rather than steering customers toward a preferred HPE tool. Detection alerts and audit events are exported via the security syslog stream. The Fluentd-based aggregator, published by HPE on GitHub, takes the raw syslog message, normalizes it to the Elastic Common Schema format, and tags the event with fields such as "event.kind: alert" and "event.severity: high," so that the receiving platform's existing rules engine can process it without custom parsing. The major difference is that this data is not only compatible with modern SIEMs; it is active. It is structured to trigger automated alerts and downstream responses, instead of being archived and consulted after the fact. Elastic Security and CrowdStrike Falcon Next-Gen SIEM are platforms explicitly validated by HPE, and the open syslog format means that Microsoft Sentinel and other modern SIEMs can be integrated with comparable effort.
Ransomware simulation on a Windows host
During remote testing conducted on the HPE Fort Collins lab, a simulated ransomware workload was executed on a Windows host connected to a Virtual Lock-protected volume on the B10000. The simulation ran a controlled encryption script that produced the high-entropy write pattern characteristic of a ransomware encryption event, without using actual malware.
The B10000 detection engine triggered an alert four to five minutes after the encryption script began writing to the volume. The alert appeared on the B10000 management console, with identification of the affected volume.
The four-to-five-minute window is short enough that immutable snapshots taken at the time of detection, or shortly after, capture a stable state before the attacker has finished traversing the volume. This method is faster than most behavioral analyses performed at the application level, because the B10000 detects writes at the block level as soon as they occur.
Respond: From alert to action
When the B10000 ransomware detection engine triggers, the platform takes automatic protective actions, even before any external system intervenes. Upon detection, the array captures an immutable snapshot of the affected volume and reports its state as degraded. This alert snapshot is not a clean recovery point and should not be used for data restoration, as it may contain encrypted data. It is intended for forensic analysis, preserving the state of the volume at the time of attack detection. It is important to note that the array does not block access to the volume. The data remains accessible, a deliberate design choice. The array triggers the alert and preserves the evidence. However, it leaves it to operators to decide on the course of action, as they are best positioned to determine whether it is a genuine attack or a false positive, such as a large legitimate encryption or compression operation.
This autonomous behavior represents the minimum, not the maximum, of response capability. Since it runs directly on the storage array, it does not depend on a SIEM rule triggering, a syslog stream functioning properly, or an external automation tool being available. Even if all other layers fail, the snapshot is preserved. This independence is essential: the most important response is triggered, whether the rest of the stack is operational or not.
