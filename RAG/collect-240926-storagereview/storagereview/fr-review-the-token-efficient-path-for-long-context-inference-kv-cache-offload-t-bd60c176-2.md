# fr-review-the-token-efficient-path-for-long-context-inference-kv-cache-offload-t-bd60c176

Enterprise AI infrastructure has moved from optimizing training models to deploying them, which changes the economics. Training represents a limited upfront investment. Inference, on the other hand, is a continuous production workload, running as long as the service is operational, and whose output is measured in tokens. This is the tokenomics problem facing AI operators: once the GPUs are installed and the energy budget is set, the profitability of the business depends on the number of tokens produced by the hardware.
In long and complex workloads, the same context is processed repeatedly by the model as conversations grow longer. The GPU has already paid to process these tokens, but when the KV cache is flushed, the system must prefill that context again. This forces the opposing system to recompute. At any scale, this is not a rounding error. It represents a real cost, in the form of energy consumption, GPU time, longer queue times, or additional hardware.
The easy solution is to buy more of the most expensive resources: more GPUs, more DRAM. Yet the recomputation has already produced reusable data. The KV cache contains only data; storing and retrieving it is inexpensive, at the cost of a slight reload overhead, offset by the high cost of the avoided prefill. The question is therefore no longer whether to keep the cache, but where to place it, and it is as much a question of cost as of performance. VRAM is the fastest resource, but also the scarcest; once saturated, the inference server begins to free up space in the cache. DRAM provides room to maneuver, but at a high and constantly rising price. This is where things change: slower than DRAM, certainly, but far cheaper per terabyte, with enough capacity to retain the context that faster resources are forced to ignore, which makes the difference between reprocessing the entire conversation and simply rereading it.
To measure the impact, we created a multi-iteration test workload on a Dell PowerEdge XE7740 server, keeping the model, GPUs, and server stack constant. The crucial figure for sizing a system is what happens once the memory tiers are saturated. Beyond that threshold, flash memory sustained approximately 30,000 tokens per second, compared to 17,000 for DRAM, thus retaining 94% of its peak while the DRAM tier dropped to 42%. Both offload tiers far outperformed the VRAM-only baseline at peak (2.9x for DRAM and 2.2x for flash memory), but that peak corresponds precisely to the moment when the DRAM tier is about to become saturated. The most expensive memory achieves the peak; flash memory sustains it as the context grows.
Before presenting the results, it is worth clarifying what the KV cache is, why it fills up, and why inference performance begins to collapse when the system has no other, less expensive location to store it.
Key takeaways
- Flash memory supports what DRAM cannot: All three configurations perform identically until memory saturation causes data eviction. VRAM saturates first, then the 512 GB DRAM tier fills approximately 45 minutes after the start of the run and begins to become saturated. Beyond that point, flash memory sustains approximately 30,000 tokens per second compared to 17,000 for DRAM, thus retaining 94% of its maximum capacity while DRAM's drops to 42%.
- Offloading recovers the throughput lost during recomputation: At peak, KV cache offloading increased total service throughput by up to 2.9x compared to the VRAM-only baseline on the DRAM tier and 2.2x on flash memory. This gain comes from the absence of prefill, since the context already computed by the GPU is reread from the offload tier instead of being rebuilt.
- It is regular users who feel the difference the most: In the worst case, the initial latency during a resumed session was 13.9 seconds with VRAM only, compared to 3.2 seconds with flash memory. System offloading limits this latency to a delay acceptable for an interactive user.
- Agent traffic makes evictions costly: One week of instrumented Claude Code traffic showed 98.16% cache reads, with only 0.02% truly cold entries.
- KV offloading is a write-intensive workload that requires high-endurance drives: Each token produced by the model creates a KV entry, and continuous TTL updates rewrite the tier continuously. At our sustained write rate, the mirrored RAID 10 array we tested represents approximately 3.2 writes per day per drive, compared to approximately 1.6 DWPD in RAID 0, which corresponds to the 3 DWPD rating of the D7-PS1030. Endurance, not capacity or speed, is the primary constraint of the flash tier, and since the cache is disposable, such intensive use of a drive dedicated to writing is an acceptable trade-off.
How inference works
Large language models are autoregressive: each output token is conditioned by all previous tokens. The attention mechanism implements this conditioning by computing (for each token in the sequence) a query vector (Q) that is compared to the key (K) and value (V) vectors of each previous token. The output of attention is a weighted combination of the values, with the weights derived from the QK dot products.
When a request arrives, it cannot be answered until the K and V tensors are available for each token. The first step, prefill, consists of the engine processing the request through the model in a single parallel pass and writing the resulting K and V tensors to memory. Prefill is therefore compute-intensive, and its latency is proportional to the length of the request.
Once prefill is complete, the engine emits the response token by token. Each new token rereads the K and V tensors of all previous tokens, computes its attention, and writes its own K and V tensors to memory for the next step. This second phase is decoding. It is sequential and limited by memory bandwidth, since generating each token requires loading into memory the cached K and V tensors for all previous tokens and computing attention over those tensors before writing the K and V tensors of the new token for subsequent steps.
The K and V tensors from both phases constitute the KV cache. Without this cache, generating token n+1 would involve recomputing the keys and values of the n previous tokens at each step, which represents quadratic complexity. Thanks to the cache, each new token computes only its own K and V tensors and reads the rest from memory, so that the cost per token remains linear.
What agentic traffic looks like
Inference is often described as being limited by memory bandwidth, because decoding predominates in the user-visible portion of the response. The actual balance between the two phases depends on the workload. A short request asking for a long text heavily stresses decoding; a long interactive request asking for a small JSON modification heavily stresses prefill. The dominant phase determines what is strained when the cache is poorly managed.
The shape of the recomputation problem follows from this balance, and the term "agentic" covers a wide range of usage patterns. Agentic coding is currently one of the most popular patterns and represents a significant share of the tokens used in OpenRouter rankings. To quantify a representative case, we instrumented Claude Code with OpenTelemetry (OTEL) logging and exported a week of traces to Grafana.
