# fr-review-the-token-efficient-path-for-long-context-inference-kv-cache-offload-t-bd60c176

<!-- source: https://www.storagereview.com/fr/review/the-token-efficient-path-for-long-context-inference-kv-cache-offload-to-flash -->

Enterprise AI infrastructure has moved from optimizing training models to deploying them, which changes the economics. Training represents a limited upfront investment. Inference, on the other hand, is a continuous production workload, running as long as the service is operational, and whose output is measured in tokens. This is the tokenomics problem facing AI operators: once the GPUs are installed and the energy budget is set, the profitability of the business depends on the number of tokens produced by the hardware.
In long and complex workloads, the same context is processed repeatedly by the model as conversations grow longer. The GPU has already paid to process these tokens, but when the KV cache is flushed, the system must prefill that context again. This forces the opposing system to recompute. At any scale, this is not a rounding error. It represents a real cost, in the form of energy consumption, GPU time, longer queue times, or additional hardware.
The easy solution is to buy more of the most expensive resources: more GPUs, more DRAM. Yet the recomputation has already produced reusable data. The KV cache contains only data; storing and retrieving it is inexpensive, at the cost of a slight reload overhead, offset by the high cost of the avoided prefill. The question is therefore no longer whether to keep the cache, but where to place it, and it is as much a question of cost as of performance. VRAM is the fastest resource, but also the scarcest; once saturated, the inference server begins to free up space in the cache. DRAM provides room to maneuver, but at a high and constantly rising price. This is where things change: slower than DRAM, certainly, but far cheaper per terabyte, with enough capacity to retain the context that faster resources are forced to ignore, which makes the difference between reprocessing the entire conversation and simply rereading it.
To measure the impact, we created a multi-iteration test workload on a Dell PowerEdge XE7740 server, keeping the model, GPUs, and server stack constant. The crucial figure for sizing a system is what happens once the memory tiers are saturated. Beyond that threshold, flash memory sustained approximately 30,000 tokens per second, compared to 17,000 for DRAM, thus retaining 94% of its peak while the DRAM tier dropped to 42%. Both offload tiers far outperformed the VRAM-only baseline at peak (2.9x for DRAM and 2.2x for flash memory), but that peak corresponds precisely to the moment when the DRAM tier is about to become saturated. The most expensive memory achieves the peak; flash memory sustains it as the context grows.
Before presenting the results, it is worth clarifying what the KV cache is, why it fills up, and why inference performance begins to collapse when the system has no other, less expensive location to store it.
Key takeaways
- Flash memory supports what DRAM cannot: All three configurations perform identically until memory saturation causes data eviction. VRAM saturates first, then the 512 GB DRAM tier fills approximately 45 minutes after the start of the run and begins to become saturated. Beyond that point, flash memory sustains approximately 30,000 tokens per second compared to 17,000 for DRAM, thus retaining 94% of its maximum capacity while DRAM's drops to 42%.
- Offloading recovers the throughput lost during recomputation: At peak, KV cache offloading increased total service throughput by up to 2.9x compared to the VRAM-only baseline on the DRAM tier and 2.2x on flash memory. This gain comes from the absence of prefill, since the context already computed by the GPU is reread from the offload tier instead of being rebuilt.
- It is regular users who feel the difference the most: In the worst case, the initial latency during a resumed session was 13.9 seconds with VRAM only, compared to 3.2 seconds with flash memory. System offloading limits this latency to a delay acceptable for an interactive user.
- Agent traffic makes evictions costly: One week of instrumented Claude Code traffic showed 98.16% cache reads, with only 0.02% truly cold entries.
- KV offloading is a write-intensive workload that requires high-endurance drives: Each token produced by the model creates a KV entry, and continuous TTL updates rewrite the tier continuously. At our sustained write rate, the mirrored RAID 10 array we tested represents approximately 3.2 writes per day per drive, compared to approximately 1.6 DWPD in RAID 0, which corresponds to the 3 DWPD rating of the D7-PS1030. Endurance, not capacity or speed, is the primary constraint of the flash tier, and since the cache is disposable, such intensive use of a drive dedicated to writing is an acceptable trade-off.
How inference works
Large language models are autoregressive: each output token is conditioned by all previous tokens. The attention mechanism implements this conditioning by computing (for each token in the sequence) a query vector (Q) that is compared to the key (K) and value (V) vectors of each previous token. The output of attention is a weighted combination of the values, with the weights derived from the QK dot products.
When a request arrives, it cannot be answered until the K and V tensors are available for each token. The first step, prefill, consists of the engine processing the request through the model in a single parallel pass and writing the resulting K and V tensors to memory. Prefill is therefore compute-intensive, and its latency is proportional to the length of the request.
Once prefill is complete, the engine emits the response token by token. Each new token rereads the K and V tensors of all previous tokens, computes its attention, and writes its own K and V tensors to memory for the next step. This second phase is decoding. It is sequential and limited by memory bandwidth, since generating each token requires loading into memory the cached K and V tensors for all previous tokens and computing attention over those tensors before writing the K and V tensors of the new token for subsequent steps.
The K and V tensors from both phases constitute the KV cache. Without this cache, generating token n+1 would involve recomputing the keys and values of the n previous tokens at each step, which represents quadratic complexity. Thanks to the cache, each new token computes only its own K and V tensors and reads the rest from memory, so that the cost per token remains linear.
What agentic traffic looks like
Inference is often described as being limited by memory bandwidth, because decoding predominates in the user-visible portion of the response. The actual balance between the two phases depends on the workload. A short request asking for a long text heavily stresses decoding; a long interactive request asking for a small JSON modification heavily stresses prefill. The dominant phase determines what is strained when the cache is poorly managed.
The shape of the recomputation problem follows from this balance, and the term "agentic" covers a wide range of usage patterns. Agentic coding is currently one of the most popular patterns and represents a significant share of the tokens used in OpenRouter rankings. To quantify a representative case, we instrumented Claude Code with OpenTelemetry (OTEL) logging and exported a week of traces to Grafana. The breakdown of this token traffic by type is presented below. Note: this Claude Code usage is on the Claude Opus 4.8 model with a context length of 1 million words, and several coding projects are running simultaneously.
Cache reads accounted for 98.16% of total token traffic. Cache creation (a previously seen prefix being prefilled following the expiration of its entry) accounted for 1.52%. Output tokens accounted for 0.30%. Truly cold input tokens accounted for 0.02%.
In a workload where 98% of traffic consists of cache reads, eviction without offloading involves prefilling most of the work the system was about to perform. The bottleneck shifts from decode bandwidth, a phase that is generally optimized, to prefill computation, already performed by the GPU in previous iterations. In fact, it is common to observe, in disaggregated serving architectures, a greater number of prefill processes than decode processes at scale, for the same reason: prefill is the control phase.
The 98% figure represents the traffic of a single user. A short chat workload would generate more cold traffic. The same would be true for a retrieval-augmented system that reinjects different documents at each exchange. This general trend holds when conversations are long, prefixes are stable, and users regularly return to the same context.
Where is the cache and what happens when it is full?
Where exactly is this cache located, and what happens when it is full? Once the model weights are loaded, the remaining VRAM is converted into KV cache space, partitioned into fixed-size blocks. At startup, the engine reports the number of tokens it can hold. This pool is the only possible location for the cache in a standard configuration without KV offloading.
GPU servers are expensive and tokens are the product, so the goal is to feed them continuously. This involves keeping the GPU loaded with a small queue of requests to process in order to avoid idle compute resources, while balancing this queue so that response latency remains in line with service level objectives (SLOs). Not all requests use their full context window; many completed key-value (KV) pairs therefore remain cached in VRAM. However, under sustained load, this cache fills up and, once saturated, the oldest entries are removed to free up space.
In an ideal world, each response would be processed in a single pass. But models are not yet capable enough; we therefore use inter-agent loops, with exchanges with a user or between agents. When the next turn arrives, if its key-value identifier is not yet in the cache, the engine reprocesses the entire conversation, including the new tokens. The context of each previous turn is reprocessed by the model, and the computation already performed by the GPU on those tokens is paid for a second, third time, and so on, for each subsequent turn. This part of the process represents a waste of resources.
What changes does KV cache offloading bring?
Instead of evicting data as soon as VRAM is full, offloading gradually distributes caches across a hierarchy: from VRAM to system memory, then to SSD. Frequently used data remains in VRAM; data that no longer fits is transferred to system memory, and if that fills up, it is in turn transferred to SSD or network storage. Actual data eviction becomes rare, because it is driven by a user-defined time-to-live (TTL) rather than memory pressure.
On the next turn, instead of recomputing tens of thousands of context tokens, we retrieve the key-value pair from RAM or flash storage. Reloading from system memory introduces a slight latency, but is far faster and more economical than recomputing the prefill. Reloading from an NVMe SSD is a little slower than a DRAM read, but remains much faster than the recomputation it replaces. Storage capacity is relatively inexpensive; GPU compute power, on the other hand, is not. Therefore, accepting a slight reload latency at the start of a turn to avoid a multi-second recomputation is overall advantageous.
How we tested
We tested this hypothesis in our lab. The system configuration was as follows:
- Server: Dell PowerEdge XE7740
- GPU: 4x NVIDIA RTX PRO 6000 Blackwell Server Edition (96 GB)
- System memory: 1 TB DDR5 (16 x 64 GB DDR5 5200 MT/s)
- Storage: 8 Solidigm PS1030 12.8 TB E3.S drives (RAID 10)
- Server stack: vLLM 0.22.0 with LMCache 0.5.0
- Model: MiniMax-M2.7
The test platform is perfectly suited to this workload. The Dell PowerEdge XE7740 server is designed specifically for enterprise AI inference. This PCIe Gen5 chassis supports up to eight double-width GPUs. The four-GPU configuration we tested is one of the most popular. It offers sufficient acceleration capacity for a wide range of inference deployments, while allowing expansion to eight GPUs based on demand. Each NVIDIA RTX PRO 6000 Blackwell Server Edition card has 96 GB of GDDR7 memory; thus, four cards constitute a substantial pool of VRAM before the cache is even stressed. Internally, the offload tier relies on eight Solidigm D7-PS1030 12.8 TB drives in RAID 10. These high-endurance Gen5 flash drives are perfectly suited to the sustained writes generated by a KV cache tier. Finally, the choice of model, MiniMax-M2.7, was, at the time of testing, one of the best open coding models that integrated with our four-GPU configuration.
We tested three configurations:
- A baseline VRAM configuration, standard vLLM without offloading, where everything that fits in VRAM is cached, and everything else is evicted.
- LMCache offloading to system memory, with 512 GB allocated to offloading.
- LMCache offloading to flash memory, with the local NVMe RAID10 array as the offload tier, preceded by a 64 GB RAM transit buffer.
We modeled the workload based on real agentic coding traffic rather than a sweep of fixed synthetic prefixes. This traffic is characterized by significant prefill and minimal decoding, with intensive prefix reuse. Sessions arrive according to a Poisson process at a rate of λ = 2.5 sessions per minute. Each session runs over multiple turns. At each turn, the model receives a short addition, typically the output of a tool or command of 250 to 600 tokens, and occasionally the reading of a file of 1,500 to 3,500 tokens. It responds with a brief reply, typically 40 to 200 tokens of tool calls or brief reasoning, and occasionally a code block of 400 to 900 tokens. Turn lengths vary by ±100 tokens. Sessions grow monotonically up to a context ceiling of 64,000 tokens, placing them in the deep context regime, where the working set exceeds VRAM capacity. The same initial load feeds all three tiers, each with a 3-minute cache warmup time.
Note regarding the memory configuration: the XE7740 shipped with 2 TB of DDR5, a high-end configuration designed to cover a wide range of projects, and whose price predated the 2026 memory price surge, which made that amount of DRAM much more expensive. The original configuration was oversized relative to the current needs of an enterprise equipped with four GPUs. To make it more realistic, we removed 1 TB of memory, keeping one DIMM per channel to preserve maximum memory bandwidth.
Methodological note regarding the flash tier: the tests used LMCache's local disk backend with its required 64 GB RAM transit buffer upstream of the array. The KV footprint retained on flash memory far exceeded the total capacity of the host DRAM during the tests; the results obtained therefore reflect disk activity rather than host memory.
Performance
Throughput under load
Total service throughput over time, as the KV working set exceeds the capacity of each tier:
Each memory tier ramps up simultaneously during the first 10 minutes, while the caches fill, with no notable difference in performance. Then, as the memory tiers fill, they diverge. The VRAM-only baseline stalls first: once VRAM is saturated, it stabilizes around 12,000 tokens per second. Each new session replaces a previous session, and the displaced cache must be entirely rebuilt when that session returns. Consequently, a greater portion of time is spent on prefill and less on decoding.
The performance of the DRAM and SSD servers continues to far exceed this threshold because, as long as their caches are not saturated, they process nearly all prefixes directly from memory or disk, without having to recompute them. The time usually spent on prefill is thus reinvested in generating new tokens.
At peak, offloading achieved a total service throughput up to 2.9x higher than the baseline on the DRAM tier (+188%) and 2.2x higher on the flash tier (+122%). Before the working set saturates VRAM, the performance of the three configurations is very close (within 1%). No memory eviction occurs, so offloading has nothing to recover. The gain only appears when memory pressure causes eviction, and it increases with server load.
The value of a larger storage tier becomes apparent when DRAM is saturated. At that load, the 512 GB RAM cache reaches saturation after approximately 45 minutes of runtime, and must then begin flushing the cache. The returned prefixes are incomplete and reloaded, which is precisely the recomputation the cache was supposed to avoid. The SSD tier, with its multi-terabyte headroom, never reaches this limit. Beyond this threshold, flash memory sustains a throughput of approximately 30,000 tokens per second, compared to approximately 17,000 for DRAM, an advantage of 75% for the SSD once RAM is saturated. In other words, after saturation, the DRAM tier delivered only 42% of its maximum throughput, while the SSD tier delivered 94%. This is the capacity scale on which the entire exercise rests: VRAM runs out first, the 512 GB DRAM tier runs out later, and a storage tier measured in terabytes rather than gigabytes practically never runs out, so it continues to provide context long after the faster tiers had to begin evicting it.
Note: the total throughput shown (several tens of thousands of tokens per second) does not correspond to the speed at which tokens are computed by the GPUs, but rather to the processing throughput of the offload tier. Total throughput counts each prefill token as input and each decode token as output for each request. Thanks to the cache, a successful request reloads the key-value (KV) pair of the prefix from DRAM or flash memory, thus avoiding a new prefill on the GPU.
Limiting the count to output tokens, i.e., the portion of throughput that a user actually waits for, gives a clearer picture:
Regarding output tokens, the three tiers again follow the same trend during cache filling, then diverge at the tipping point. The DRAM tier peaks near 300 tokens per second, an increase of 75% over the baseline, before gradually declining as it begins to flush caches; the flash tier holds around 250 tokens per second until the end of the run, an increase of 46% over the baseline. The performance of the RAM and SSD tiers remains broadly similar (within about 10%) until the DRAM tier saturates; after that, the gap widens.
Time to first token: what the user waits for
Throughput measures total token production. Time to first token measures what a user experiences: the wait between the moment they click "Send" and the moment they receive the first token. We plot it over the course of the run, at its median, as the working set grows and each tier fills.
As long as the caches are active, all three tiers return a first token in about half a second. Then their performance diverges, following the evolution of their throughput. The baseline collapses first: its response time exceeds 10 seconds from the start of the run, while the DRAM tier stays below the 1-second (TTFT) mark much longer, until its 512 GB are saturated around the 45th minute. Its latency then drops sharply when it begins to flush and recompute data. The SSD tier degrades most gradually and shows the shortest response time of the three over the second half of the run.
This reversal perfectly illustrates the tiering debate. DRAM is the fastest as long as the working set fits its category; flash memory becomes the fastest when it no longer does, because it retains contextual information that DRAM has begun to evict.
The problem of returning users
The latencies shown above concern exchanges within a continuous session. The case of a user resuming their session is different: a session is interrupted mid-conversation, remains inactive for about fifteen minutes, then resumes where it left off. We modeled this with a group of users who became inactive after about twenty exchanges and were reactivated 15 minutes later, a period sufficient for a busy server to process other requests through its caches. Eleven of these reactivations occurred within the measurement window of each tier. Since the workload is identical for all tiers, the same eleven sessions were reactivated in each run, allowing a direct comparison of resume times. The graph below shows the median time to first token for each tier during a normal exchange, compared to the resume time. The error bar indicates the longest resume time in the sample.
On average, the figures confirm the predictions of the mechanisms, and the tiers rank in the expected order. DRAM comes first: an inactive session resumes in 0.6 seconds, barely more than the 0.5 seconds of a normal session. The SSD ranks second with 0.8 seconds; we know that an NVMe read is slower than a DRAM read, and this is partly reflected in these results. The VRAM-only baseline is the slowest at 1.4 seconds; lacking data to offload, the prefix of the inactive session was evicted from GPU memory for active traffic, and the first resume must recompute it. At best, the total gap is only about one second.
The best-case scenario is not where the choice is made. The worst of the eleven reload times at each tier is as follows: 0.8 seconds on DRAM, 3.2 seconds on SSD, and 13.9 seconds on the baseline. The tolerance for a fourteen-second wait for a first token, or its impact on the service level objective (SLO), depends on the service. For any interaction, the second option prevails, and only the offload tiers keep this wait within a limit acceptable to the user. This delay also varies with context, because the cost of recomputation is proportional to the user's history: in the deeper contexts of the throughput test, the baseline wait time far exceeds 14 seconds, while DRAM and SSD result in only a limited reload.
Choosing and sizing the KV cache
Both offload tiers far outperform the VRAM-only baseline, and their performance is very close. The gap is small because the throughput gain comes solely from freeing up VRAM, and the same amount is freed whether the evicted cache is stored in DRAM or on SSD. Throughput is independent of the cache's original storage tier. Latency, on the other hand, is sensitive, because a DRAM read is faster than an NVMe read, but both options remain inexpensive compared to fully recomputing the same key-value pair.
The choice between the two solutions rests on a trade-off between service level objective (SLO) and cost, which depends on the operator's optimizations. Keeping the entire offloaded cache in RAM offers the best latency, but represents a significant investment for a relatively small latency gain compared to flash memory. Tiering constitutes a compromise: a smaller RAM tier absorbs latency-critical accesses, while an additional storage tier hosts less frequently accessed caches whose response time is not critical (a few hundred milliseconds).
One can also consider key-value caches in terms of their size. Sizing the storage tier depends on the maximum token throughput the system can support. The storage space required for key-value caches equals the throughput multiplied by the time-to-live (TTL) of the cache entries. Each token produced creates a key-value entry; the calculation therefore boils down to multiplying the token arrival rate by their retention duration. The two default TTL values in production are five minutes and one hour.
Let us calculate the KV cache size for MiniMax-M2.7 in FP8, as tested here. With one byte per KV element, the entry per token is 2 × 62 × 8 × 128 bytes, or approximately 124 KiB. This calculation generalizes to any grouped-query attention transformer: the KV cache size per token equals the number of layers × the number of KV heads × the head dimension × 2 (for K and V) × the number of bytes of the data type. Thus, a model with more layers or KV heads writes proportionally more information per token. Under moderate operating conditions (approximately 4,200 tokens per second on the RAM tier), one hour of retention generates approximately 15 million cached tokens, which, at 124 KiB per token, represents approximately 1.8 TB. This represents a significant amount of DRAM and increases the compilation cost.
From this perspective, SLO requirements and budget determine the choice of cache tier. If the SLO is flexible enough that the reload latency of the SSD tier remains acceptable, the second KV cache tier can rely solely on storage, with only the thin RAM buffer required by upstream connectors. The cost of storage is modest: during our tests, peak KV traffic reached 4.1 GB/s write and 1.1 GB/s read, for a maximum throughput measured by fio of approximately 114 GB/s. The RAID 10 array used had 28 times that bandwidth, ensuring that flash storage is not a bottleneck, even when the XE7740 fully utilizes its eight GPUs and supports a larger simultaneous load. This headroom allows the operator to prioritize capacity over speed. Each additional terabyte of D7-PS1030 extends the time-to-live (TTL) and the working set that the system retains in residence, and a larger resident cache means more avoided recomputations and more tokens served.
Endurance is the constraint that defines this tier. A KV offload cache is very write-intensive: each token produced by the model creates a KV entry, and TTL updates cause continuous cache rewriting, so the drives are constantly stressed by writes. On our eight-drive array, the sustained write throughput reached 1.9 GB/s. With the RAID 10 configuration we tested, mirroring doubles the capacity absorbed by the media, which corresponds to approximately 3.2 writes per day on each 12.8 TB drive, slightly above the 3 drive writes per day (DWPD) sustained rating of the D7-PS1030. For primary storage, this rate would be prohibitive, but it is acceptable in this specific case. The cache is designed to be ephemeral, and the failure mode of a worn drive is recomputation, not data loss. RAID 0 is arguably more suitable for this tier for some users, as it distributes data across the eight drives to avoid duplicate writes and reduces the media write rate to approximately 1.6 DWPD, which remains well within allowable limits. In both cases, the conclusion remains the same: this workload consumes endurance faster than any other element of the system, high-endurance dedicated drives have only a fraction of the capacity needed for this level of performance, and it is this combination that makes a high-capacity, write-focused drive like the PS1030 the ideal choice.
Tokens per dollar
The performance section demonstrated that flash memory retains most of the throughput and maintains time to first token, unlike DRAM, when the working set exceeds memory capacity. From a business perspective, the cost of the storage tier is a determining factor. The simplest solution for recomputation is to increase the cost of that expensive DRAM; the case for offloading is only valid if the storage tier is significantly cheaper per unit of capacity.
The most obvious gap lies in capacity, not price. The 512 GB DRAM offload tier is the one that saturated and began flushing the cache; the flash tier, measured in terabytes, is the one that did not. No realistic DRAM budget allows for tens of terabytes of KV cache to be placed near the GPUs. Therefore, beyond a certain context length, the choice is no longer between fast DRAM and flash memory; it is rather a choice between flash memory and context deletion, with deletion being the main cause of throughput loss and latency.
In terms of price, enterprise flash memory has long sold at a fraction of the cost per terabyte of DRAM, a structural gap that stems from the multi-level, 3D-stacked cell design of NAND, as opposed to the one-transistor-one-capacitor design of DRAM. The memory shortage expected for 2026 has driven both prices up significantly, and NAND contract prices have risen at least as fast as DRAM prices throughout the year. So this is not a case of flash memory prices falling due to the DRAM price surge. Even at current levels, the price gap per terabyte persists, and flash memory remains the only solution offering terabyte-scale cache capacity at a cost compatible with a deployment budget.
Throughput and cost converge. At the moment flash memory took the lead, it was processing more tokens per second than DRAM, not fewer. It therefore does not sacrifice throughput for capacity, but offers increased capacity on a less expensive medium per terabyte. In terms of tokens per second per dollar, the advantage is considerable for flash memory, and it grows with data retention duration, because that is precisely where DRAM reaches its limits, unlike flash memory.
DRAM remains the most appropriate memory as long as the working set supports it, and the thin RAM transit buffer required by connectors is always upstream of flash memory. However, adding additional GPUs or DRAM represents the highest cost per terabyte to obtain maximum performance only needed for the workload, until the cache saturates. Offloading or tiering to flash memory preserves most of that performance while maintaining context indefinitely, at an affordable cost per terabyte. The final decision will, however, depend on the service level objective (SLO) requirements of the workload the operator is optimizing.
Conclusion
For inference workloads, tokenomics is at the heart of the debate. The token is the product, and recomputation is waste: the GPU has already generated that context and is forced to rebuild it. Agentic serving is where the stakes are highest, because our week of instrumented Claude Code traffic showed that 98.16% of tokens were cache reads, a context that the GPU had already computed and would otherwise have rebuilt at each eviction. KV cache offloading transforms the prefill computation, which would have served to rebuild that history, into new tokens. On the XE7740, this translated into a total service throughput up to 2.9x higher than the VRAM-only baseline under heavy load, with the model, GPUs, and engine held constant. Where DRAM was saturated and its performance was dragged down, flash memory sustained that throughput with a capacity DRAM cannot match.
This does not, however, call into question the need for DRAM. For short and irregular workloads, where a session opens, runs briefly, and closes before its cache saturates memory, DRAM is the optimal solution, and KV cache offloading provides little benefit. The working set fits, latency is minimal, and there is nothing to evict.
We consider this profile to be the exception, however, where a DRAM tier suffices. Most production inference now runs continuously and over long periods: multi-turn agents, large contexts, steady concurrency, users rejoining the same session. In this case, the working set exceeds the capacity of the memory tier an operator can allocate, the cache is flushed, and the GPU is called back into service to rebuild the context it has already produced. This is the most costly failure mode, and it is common.
For these workloads, offloading the KV cache to flash memory offers a dual advantage. It allows GPUs to produce new tokens instead of recomputing old ones, which corresponds to the tokenomics efficiency measured by this operation. In addition, it places the necessary capacity on the most cost-effective durable memory tier of the system. The main advantage over server configuration lies in reduced DRAM consumption: a server using flash memory for the cache can be specified with much less DRAM. Given the price of memory in 2026, this is one of the most significant savings in the quote. The token is the product, and for the long-context workloads that now dominate server serving, the most token-efficient solution is the one that avoids paying to produce the same tokens twice; that solution goes through flash memory.
