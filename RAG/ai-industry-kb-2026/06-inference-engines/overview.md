# 6. Inference Engines
Keywords: vLLM, inference engines, PagedAttention removal, Model Runner V2, V0 deprecation, vLLM-Omni, GGUF plugin, disaggregated serving, prefill-decode disaggregation, NIXL, LMCache, KV connectors, llm-d, NVIDIA Dynamo, Inferact, spend flip, MLA, DeepSeek V4, sparse MLA, Kimi-K3, TurboQuant, speculative decoding, XGrammar, NIM 2.0, AWS Inferentia, vllm-neuron, TPU inference, FlashAttention 4, structured generation, enterprise adoption

## Summary

By September 2026, **vLLM is the industrial generalist standard for open-source GPU inference serving**: the default engine in production deployments, the sole LLM/VLM backend of NVIDIA NIM 2.0 (per third-party analysis), the engine behind Stripe's reported 73% cost reduction on 50M daily API calls, and the reference backend for the Kubernetes-native llm-d disaggregated-serving project. It consolidated this position during the 2026 **"spend flip"** in which inference overtook training economically — Gartner (reported August 2026) puts 2026 global AI-optimized IaaS at $42B (+96% YoY), with inference workload spending ($23.3B) surpassing training ($19B): 55% of AI-optimized IaaS in 2026, forecast 59% in 2027. With inference as the dominant consumption model, the inference runtime became a first-order cost decision, and vLLM captured the broad middle while SGLang captured the prefix-heavy/agentic niche (tracked in sibling part 06b).

**The engine was almost entirely rewritten in 2026.** The legacy V0 `AsyncLLMEngine` core was fully removed in **v0.16.0 (March 2026)** — the V1-only milestone is five months older than the v0.28.0 date a brief had attached to it (RFC #18571 planned the removal; an independent forensic review of v0.16.0 confirmed the V0 fallback no longer exists at binary level). **PagedAttention, vLLM's landmark 2023 algorithm, was deleted from the main internal path in v0.25.0 (July 2026)** by PR #47361, now that the V1/Model Runner V2 backends are standard — it survives only as a legacy attention path and must **not** be presented as the current core mechanism. **Model Runner V2 became the default execution path for all dense models** in the same release, with full CUDA-graph decode capture; the Transformers v5 modeling backend reached native-speed parity (PR #47187).

**vLLM v0.28.0 was tagged 2026-08-26 (584 commits, 270 contributors)** — a *core* vLLM release, correcting Wave 2's "vLLM-Omni v0.28.0" mislabel: headliners are the Kimi-K3 performance push (Decode Context Parallel, FlashKDA kernels, SiTU for MegaMoE, ~17 GiB/GPU shared-expert sharding savings), end-to-end sparse MLA for DeepSeek V4 (plain decode, MTP, DSpark speculative decoding), Model Runner V2 maturation (E/P/D disaggregation, weight offloading), and tiered KV-cache offloading including **disk offloading** and out-of-tree secondary tier managers (KV-cache mechanics live in §7). v0.26.0 (between, 411 commits/212 contributors) carried the DeepSeek-V4 performance push (specialized routing, sparse decode/prefill optimizations) and matured KV offloading with an object-store secondary tier, DP-replica-aware tiering, and encoder-cache connectors including CPU offload. v0.27.0 (September 2026) is the current ROCm-era release; a v0.29.0 community production attempt was logged 2026-09-09 [DIRECTIONAL] — any "latest version" claim must be date-stamped.

**GGUF support was split out of vLLM core.** In v0.24.0 (mid-2026) in-tree GGUF support was removed (PR #39612; migration tracked in RFC #39583) and moved to the out-of-tree **`vllm-gguf-plugin`** (`vllm-project/vllm-gguf-plugin`): GPU-only (CUDA/ROCm, not CPU), `<hf_repo>:<quant_type>` addressing (e.g. `unsloth/Qwen3-0.6B-GGUF:Q4_K_M` [UNVERIFIED as executed end-to-end]), tensor-parallelism support, Triton dequant and llama.cpp-style CUDA vec-dot kernels. As of September 2026 the plugin is young with documented per-model-family bugs (no Gated-DeltaNet hybrid support as of 2026-07-28 — Qwen3.5/3.6 MoE, tracking issue #80; without a registered quant method, `FusedMoE` dequantizes all experts to bf16, ~160 GB needed vs 121 GB available on one reported setup); operator guidance is to serve safetensors when reliability matters.

**vLLM-Omni** (`vllm-project/vllm-omni`) extends vLLM to fully disaggregated **any-to-any multimodal serving**: three independent GPU pools (modality encoders, prefill, decode) sized to their compute profiles, a stage abstraction with per-stage batching, a unified AR/DiT paged KV cache runtime (introduced in its v0.28.0 line), and NIXL-based feature/KV transfer between stages. Officially released 2025-11; paper arXiv:2602.02204 (2026-02-02) reports up to 91.4% lower job completion time vs baselines [UNVERIFIED as independently reproduced]. Serving surface includes `/v1/audio/speech`, `/v1/images/generations`, `/v1/videos`, `/v1/chat/completions` (multimodal); model coverage as of 2026-08 spans Qwen3-Omni, MiniCPM-o 4.5, TTS families (Qwen3-TTS, CosyVoice3), diffusion (Wan2.2, FLUX, MiniMax H3), and robot-policy/action models (GR00T-N1.7, InternVLA-A1). AWS Deep Learning Containers ship vLLM-Omni images (CUDA 13.0, FlashInfer, DeepEP, LMCache + NIXL, EFA/OpenMPI).

**Commercialization arrived in 2026.** **Inferact launched 2026-01-22 with a $150M seed at an $800M valuation** (co-led by Andreessen Horowitz and Lightspeed Venture Partners), formed by vLLM creators with Simon Mo as CEO, to commercialize vLLM. Red Hat's AI Inference Server (hardened vLLM + Neural Magic compression, announced May 2025, current through 2026) claims 2–4x token production with pre-optimized models [VENDOR] and publishes AI Validated Models on Hugging Face. A Futurum Group analysis (2026-08-29) calls vLLM the **"de facto open-source LLM inference engine"**, and vLLM is prominent across the PyTorch Conference NA 2026 program (2026-10-20–21, San Jose — post-cutoff, program-only evidence as of 2026-09-22). ISG (September 2026) reports 65% of organizations piloting open-weight AI and ~20% with a local LLM deployed — a demand tailwind for the open engine layer.

**The 2026 architecture pattern is disaggregation.** Prefill, decode (and for vLLM-Omni, encoders) run in independently sized pools, with KV blocks and modality features moved by the **NIXL** fabric (NVIDIA Inference Xfer Library — used as the KV transfer layer by vLLM's NixlConnector, NVIDIA Dynamo's KVBM, SGLang, TensorRT-LLM, LMCache, and llm-d) over RDMA/NVLink/TCP. vLLM's KV connector landscape: NixlConnector (single-cluster RDMA/NVLink default; metadata server is a startup SPOF), LMCacheConnector (cross-instance cache sharing, HBM→DRAM→NVMe tiering, global prefix index), MooncakeConnector (cluster-scale shared cache pools), MooncakeStoreConnector (tiered offload via a distributed master store) — distinct from vLLM-Omni's higher-level OmniConnector between heterogeneous stages. Above the engines, the battle moved to orchestration: **NVIDIA Dynamo (1.0, mid-2026)** vs the Kubernetes-native **llm-d** (Red Hat/Google/IBM/NVIDIA/CoreWeave). Both compete on orchestration while sharing the data plane — llm-d explicitly intends to reuse NIXL. AWS ships EKS blueprints for disaggregated vLLM/SGLang/TensorRT-LLM; llm-d's own v0.5 benchmarks claim up to 57x TTFT gains vs naive routing under prefix reuse [VENDOR], with operators' own measurements more conservative (~25% over defaults).
