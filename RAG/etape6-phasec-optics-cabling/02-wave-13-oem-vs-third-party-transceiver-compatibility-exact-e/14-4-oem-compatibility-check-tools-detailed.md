# 14.4 OEM compatibility-check tools — detailed

| **MikroTik** (RouterOS) | **No restrictions:** "MikroTik devices and SFP, SFP+, SFP28, QSFP+, and QSFP28 modules do not have any restrictions for other vendor equipment. … as long as the other vendor modules and devices comply with transceiver multisource agreement (MSA) they should be compatible with MikroTik" [official-mirrored] (https://my.mbuzztech.com/portal/en/kb/articles/https-help-mikrotik-com-docs-display-ros-mikrotik-wired-interface-compatibility). | Fully open, MSA-compliance is the stated requirement [official-mirrored]. | **MikroTik wired-interface compatibility wiki** with per-device tables (1G SFP, 10G SFP+/25G SFP28, 40G QSFP+, 100G QSFP28, breakout support) [official-mirrored]. No interactive web tool — not found. | No vendor lock, no TAC-gating documented — nothing beyond the no-restriction statement found. |
| **Juniper** (Junos) | **No vendor-ID lock** enforced; third-party optics generally link up; no official err-disable/lock behavior documented [official stance inferred from JTAC policy + absence of lock documentation]. Official JTAC policy (100G and 1.6T Optics & Cables Guides): "We recommend that you use only optical transceivers and optical connectors purchased from Juniper Networks… JTAC provides complete support for Juniper-supplied optical modules and cables. However, JTAC does not provide support for third-party optical modules and cables that are not qualified or supplied by Juniper Networks. … Your JTAC engineer will likely request that you check the third-party optical module or cable and, if required, replace it with an equivalent Juniper-qualified component. Use of third-party optical modules with high-power consumption (for example, coherent ZR or ZR+) can potentially cause thermal damage to or reduce the lifespan of the host equipment. Any damage to the host equipment due to the use of third-party optical modules or cables is the users' responsibility. Juniper Networks will accept no liability for any damage caused due to such use." [official] (https://juniper.net/documentation/us/en/hardware/100g-optics-cables-guide/100g-optics-cables-guide.pdf and https://www.juniper.net/documentation/us/en/hardware/1.6t-optics-cables-guide/1.6t-optics-cables-guide.pdf). Older Junos release notes (12.1X46, 9.6): "We strongly recommend that only transceivers provided by Juniper Networks be used… We cannot guarantee that the interface module will operate correctly if third-party transceivers are used" [official] (juniper.net release notes). | No lock; recommendation + support boundary, with an explicit thermal-damage warning for high-power coherent ZR/ZR+ (user's responsibility) [official]. | **Juniper Networks Pathfinder Hardware Compatibility Tool (HCT)** [official] (https://apps.juniper.net/hct/) — e.g. https://apps.juniper.net/hct/model/?component=JNP-QSFP-100G-PSM4, https://apps.juniper.net/hct/model/JNP-SFP-10G-BX40U. Inputs: hardware model / component (transceiver part number, platform). Outputs: part number (740-xxxxx), speed, breakout capability, form factor, connector type, DOM availability. **Lists only Juniper-supplied optics (no third-party lookup)** [official]. | JTAC "does not provide support for third-party optical modules and cables that are not qualified or supplied by Juniper Networks"; will help diagnose host-related issues if JTAC judges the issue unrelated to the optic; will likely ask to swap to a Juniper-qualified component [official] (same guides). Optics verified via standard DDM (`show interfaces diagnostics optics`) [official]. |
| **NVIDIA / Mellanox** (Spectrum, Cumulus, MLNX-OS) | No public official statement found on third-party optic support/allowance for Spectrum switches — **not found** for an explicit policy page. NVIDIA firmware release notes ship per-product **"Validated and Supported Cables and Modules"** tables listing only NVIDIA part numbers with lifecycle phases (e.g. ConnectX-7 firmware release notes, "3.3 Validated and Supported Cables and Modules") [official] (https://docs.nvidia.com/nvidia-connectx-7-adapter-cards-firmware-release-notes-v28-39-2048-lts.pdf; also "Firmware Compatible Products" pages at docs.nvidia.com). NVIDIA Cumulus Linux port diagnostics include code **1025** "Long Range for non Mellanox cable/module": "Non-NVIDIA long-distance cables/modules are not supported" → recommended action "Replace with genuine NVIDIA original parts"; code **1027** "Bad/unsupported EEPROM"; **1028** "Part number list" (transceiver not in the supported part-number list → replace with cable from the supported list) [secondary — mirrored from NVIDIA Cumulus Linux docs via manuals.plus PDF; official docs.nvidia.com wording not directly verified this round]. Community consensus: Spectrum/Cumulus switches generally accept third-party optics (no Cisco-style hard lock); NVIDIA support will ask to reproduce with genuine parts — [unverified/secondary]. | Validation-list-based rather than lock-based in the documents found; official third-party statement absent [secondary/official]. | Per-product firmware release notes "Validated and Supported Cables and Modules" sections [official] (docs.nvidia.com). No single interactive optics-compatibility tool found — not found. | No official third-party-optic support statement found — not found. |
