# 2. ORMs, query builders, and schema migrations

## 2. ORMs, query builders, and schema migrations

### 2.1 The ORM landscape by language (2026)

- **Python:** SQLAlchemy 2.0 is the typed standard (`Mapped`/`mapped_column` style); async support via `asyncpg`/`psycopg`; SQLModel is a thinner ergonomic layer over SQLAlchemy favored with FastAPI; Django ORM remains the full-stack default `[secondary]`.
- A 2026 ADR recorded a team choosing SQLAlchemy 2.x over SQLModel and raw asyncpg for typed access plus Alembic migrations, citing enterprise prevalence and reviewability `[secondary]`.
- **TypeScript/Node:** Prisma (migrated in v7 from its Rust query engine to TypeScript/WASM with driver adapters, per 2026 ecosystem notes), TypeORM, MikroORM, Drizzle, and Kysely (type-safe query builder, not a full ORM) `[secondary]`.
- **Java/Kotlin:** Hibernate/JPA remains dominant; jOOQ for type-safe SQL-first access `[secondary]`.
- **Go:** GORM, sqlc (generates typed Go from SQL — the SQL-first counterpoint to ORMs), ent `[secondary]`.
- **Rust:** Diesel, SeaORM, sqlx (compile-time checked queries, no runtime ORM) `[secondary]`.

### 2.2 ORM escape hatches every developer should know

- N+1 queries remain the canonical ORM failure: solve with eager loading (`selectinload`, `joinedload`, Prisma `include`), not by disabling lazy loading globally `[independent]`.
- Autogenerated migrations are drafts: Alembic's docs and community guidance stress that `--autogenerate` output must be reviewed and edited — it misses constraints, data migrations, and destructive-op nuances `[secondary]`.
- For aggregation/reporting queries, raw SQL via the ORM's connection (SQLAlchemy `text()`, Prisma `$queryRaw`) is usually faster to write and tune than contorting the query builder `[independent]`.
- MongoDB/Mongoose: avoid hydrating full documents on hot paths; use `.lean()`, projections, and aggregation pipelines instead of model instances for reads `[secondary]`.

### 2.3 Alembic (Python/SQLAlchemy)

- Alembic is the de-facto migration framework for SQLAlchemy; current stable line is **1.18.x** (issue reports in 2026 reference Alembic 1.18.4 with SQLAlchemy 2.0.51, PostgreSQL 18.4, Python 3.14.5) `[secondary]`.
- Migrations are versioned Python scripts organized as a DAG: each file has `revision`, `down_revision`, and `upgrade()`/`downgrade()` functions emitting SQLAlchemy Core ops or raw SQL `[secondary]`.
- `alembic upgrade head` walks the revision graph from the database's current revision to the tip; branches are resolved with merge migrations `[secondary]`.
- `env.py` bridges Alembic and the app: configures engine/URL, sets `target_metadata` (all models imported), and defines offline/online migration runners `[secondary]`.
- Workflow: `alembic revision --autogenerate -m "..."` → review/edit generated file → `alembic upgrade head` → commit migration with the model change; CI runs `alembic upgrade head` before tests `[secondary]`.
- Known gap: unimported model modules are silently skipped by autogenerate — every model module must be imported where `target_metadata` is assembled `[secondary]`.

### 2.4 Flyway (JVM-first, polyglot via CLI)

- Flyway is the dominant JVM-ecosystem migration tool (Redgate-owned since the 2022 acquisition); versioned SQL migration files (`V1__...sql`) applied in order with checksum verification `[secondary]`.
- Supports Java-based migrations for logic SQL cannot express; editions range from Community to Teams/Enterprise with differing feature gates `[secondary]`.
- Compared with Alembic: Flyway is SQL-first and opinionated about linear versioning; Alembic is Python-first with DAG revisions and autogenerate-from-models `[independent]`.

### 2.5 Prisma Migrate

- Prisma Migrate generates SQL migrations from schema changes in the Prisma schema file; the 2026 ecosystem notes describe Prisma 7 moving away from its Rust query engine toward TypeScript/WASM and driver adapters — verify details against official Prisma sources before relying on them `[secondary]`.
- Shadow-database diffing lets Prisma Migrate detect drift between the declared schema and the actual database `[secondary]`.

### 2.6 Migration discipline (engine-agnostic)

- One logical change per revision; never hand-edit the database outside the migration tool — schema changes must be reviewable, reversible, and applicable identically in dev and CI `[secondary]`.
- Expand/contract pattern for zero-downtime changes: add new column/table (expand), dual-write/backfill, switch readers, then drop the old (contract) `[independent]`.
- Separate schema migrations from data migrations: large backfills should run as batched, idempotent jobs (not inside a single DDL transaction) to avoid long locks `[independent]`.
- `alembic stamp` / baseline operations exist to adopt the tool on an existing database without replaying history `[secondary]`.
