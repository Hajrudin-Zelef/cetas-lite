# fortigate-3-troubleshooting-tip-how-to-troubleshoot-ha-heartbeat-packet-lost-iss-70669b4b

Troubleshooting Tip: How to troubleshoot HA 'Heartbeat packet lost' issues in a FortiGate HA Cluster
| Description | This article describes 'Heartbeat packet lost' errors in HA log messages and offers ways to identify the root cause and fix it. | 
| Scope | FortiGate running in HA mode (FGCP HA Active-Passive or Active-Active). | 
| Solution | When a FortiGate is running in HA FGCP mode, Active-Passive or Active-Active, HA Log messages may appear indicating there was a 'Heartbeat packet lost':  This log message means that the HA Peer did not receive the HA Heartbeat packet within the HA Hold-down timer. For example, if the Heartbeat packets are not received within 1.2 seconds (1.2 seconds is the default value - a calculation is shown below). For more information, refer to this document: HA heartbeat interface. This article provides the troubleshooting tips required to narrow down the cause of this issue. Troubleshooting steps: Run 'get system ha status' to see if there are dropped packets or errors on the heartbeat interface: get system ha status \| grep "ha1" ha1: physical/10000auto, up, rx-bytes/packets/dropped/errors=8013531615/5586193/486/0, tx=256040866/180012/0/0 ha1: physical/10000auto, up, rx-bytes/packets/dropped/errors=8005393949/5575798/549/0, tx=261722674/182376/0/0 Run the command below to see if there are dropped packets in the physical interface counters: diagnose hardware device info nic <heartbeat port number>diagnose hardware deviceinfo nic ha1 \| grep drop rx_dropped 4333 tx_dropped 0 port.rx_dropped 0 port.tx_dropped_link_down 0  diagnose debug application hatalk -1 diagnose debug application hasync -1 diagnose debug enable To disable the debug after collecting the output: diagnose debug disable  diagnose debug reset<hatalk> cfg_changed is set to 0: hatalk_packet_setup_heartbeat <hatalk> setup new heartbeat packet: hbdev='port22', packet_version=473 <hatalk> options buf is small: opt_type=41(DEVINFO), opt_sz=13806, buf_sz=8726 <hatalk> pack compressed dev_info: dev_nr=37, orig_sz=13800, z_len=244 The output of  'diagnose sys top' can be used to verify whether there is high CPU usage with the 'hatalk' process. Having high CPU usage in the hasync process should not directly affect the heartbeat packet processing. However, if it is high and if both processes are running on the same CPU core, it could have an indirect effect. Similarly, if there is constant high CPU usage due to other processes, that needs to be addressed as well.   Verify these issues with the following commands: get system performance status CPU states: 0% user 99% system 0% nice 1% idle 0% iowait 0% irq 0% softirq CPU0 states: 0% user 99% system 0% nice 1% idle 0% iowait 0% irq 0% softirq CPU1 states: 0% user 98% system 0% nice 2% idle 0% iowait 0% irq 0% softirq diagnose sys mpstat 1 diagnose sys profile ? start    start kernel profiling data stop     copy kernel profiling data show     show kernel profiling result sysmap   show kernel sysmap cpumask  profile which CPUs [Take 0-10 arg(s)] step     set profile step module   show kernel module   fnsysctl cat /proc/interrupts fnsysctl cat /proc/softirqs For example, the output of the command 'fnsysctl cat /proc/interrupts' shows that the TxRx Queues of ha1 heartbeat interface [i40e-ha1-TxRx-31, i40e-ha1-TxRx-33] are mapped to CPU core CPU75 and CPU77, respectively.  Similarly, it is necessary to find the core numbers for other host queues of the heartbeat interface and verify if there are CPU spikes on these cores. Take action as necessary if these are present. The following command can be used to find the counters for errors, so run it multiple times: fnsysctl ifconfig <ha interface name>  Note: fnsysctl commands require super admin permissions. diagnose hardware device info nic <ha interface name> The command also displays interface statistics. In multi-VDOM environments, run this command from the global VDOM.   In some network environments, increasing the values of 'hb-interval' and 'hb-lost-threshold' to a higher value may resolve the problem.  Example: config system ha     set hb-interval 10 (default =2)     set hb-lost-threshold 40 (default=20) end Adding a backup heartbeat interface to an HA cluster is highly recommended. In the event of heartbeat packet loss, the backup interface helps maintain network stability by preventing an HA split-brain state. The backup heartbeat is limited in terms of synchronization features, as its goal is primarily to maintain member placement and avoid both cluster members declaring themselves as primary during disruption of regular heartbeat traffic. config system ha     set backup-hbdev <interface list> end The backup-hbdev is used only when the secondary unit fails to detect heartbeats from the primary unit.
